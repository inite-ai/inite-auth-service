# AGENTS.md — working in inite-auth-service

Instructions for AI coding agents (Claude Code, Cursor, Codex, Copilot coding
agent, Gemini CLI, Windsurf, …) and the humans driving them. Every command and
path below exists in this repo; if one turns out wrong, fixing it is a welcome
PR.

## What this is

INITE Identity Provider: a self-hosted OAuth 2.1 / OpenID Connect authorization
server (NestJS 11, Prisma 7, Postgres, Redis) with passkeys, agent identities,
Web3 sign-in, SCIM, SAML SP and CAEP, plus a Next.js login/admin/docs UI in
`frontend/`.

In the **INITE Triad** this is the **issuer**: Auth mints every access token
and publishes the JWKS; Billing and Brain only verify. The claim shapes,
issuers, audiences and key rotation order are governed by the Triad contract —
<https://github.com/inite-ai/inite-triad/blob/main/docs/compatibility.md> — and
where this repo disagrees with it, the contract wins.

## Ground rules (non-negotiable)

1. **Never edit a shipped migration** in `prisma/migrations/`. Schema changes
   are a new `NNNN_description/migration.sql`, next number in sequence.
   `scripts/migrate.js` is the only migration path (fresh installs and
   upgrades alike) — do not add another one, and do not use `prisma db push`
   for anything you commit.
2. **Never change token claim shapes** (`iss`, `aud`, `sub`, `org`/`org_id`,
   scopes, lifetimes) or the JWKS/kid behaviour without an approved issue. A
   change to the meaning of a claim follows the contract's §7 overlap policy
   and updates the issuer-side conformance tests
   (`src/oauth/__tests__/client-credentials-resource.spec.ts`,
   `refresh-keeps-audience.spec.ts`).
3. **Never weaken a security default to make something work**: PKCE (S256
   only), audience binding, refresh-token rotation and reuse detection, DPoP,
   HMAC checks, rate limits, CSP, admin guards. If one is in the way, stop and
   ask.
4. **Never log or return secrets or PII**: tokens, client secrets, password
   hashes, TOTP secrets, refresh-token hashes, full emails in error paths.
   Strip secret columns with the helpers in `src/common/sanitize.ts`.
5. **Never commit secrets**, not even in tests — use obvious dummies.
   `gitleaks` runs on every PR (`.github/workflows/security.yml`).
6. **Never skip or delete a failing test to get green.** Fix the code or ask.
   Auth-flow changes need a test for the *security property* (e.g. "a rotated
   refresh token is rejected on reuse"), not just the happy path.
7. **Never hand-edit generated files**: the Prisma client (regenerated by
   `npm install` → `postinstall: prisma generate`), `dist/`, `openapi.json`,
   `frontend/.next/`, `CHANGELOG.md` and `.release-please-manifest.json`
   (release-please owns both).
8. **No new dependency without a one-sentence reason in the PR**; be extra
   wary of crypto/JWT/session libraries. Prefer the incumbents (`jose`,
   `@simplewebauthn/server`, `bcryptjs`, `ethers`).
9. **Don't bypass the lint gates** by raising a ceiling or adding a blanket
   `eslint-disable`. Split the file or function instead.

## Setup

**Codespaces / devcontainer (recommended, one click).** Open the repo in
GitHub Codespaces (or "Reopen in Container" in VS Code). `.devcontainer/`
starts Node 24 with Postgres 15 and Redis 7, runs `npm ci` for backend and
frontend, copies `.env.example` to `.env` if missing, and migrates the
database. The container's environment (`.devcontainer/docker-compose.yml`)
already points `DATABASE_URL`/`REDIS_*` at the service containers and wins
over `.env`. Then `npm run start:dev` → <http://localhost:3002/health>.

**Local, without a database** — enough for lint, build and the whole unit
suite (it mocks Prisma and Redis):

```bash
npm ci                       # Node 24 (what CI and the Dockerfile use)
(cd frontend && npm ci)      # only if you touch the UI
```

**Local, with a database** — `docker compose up -d postgres redis` (root
`docker-compose.yml`). Note: that compose publishes Postgres on host port
**5434** (user `postgres`, db `auth`, password `POSTGRES_PASSWORD`) and Redis
on **6381**, which `.env.example` does not match yet (issue #245). Override in
`.env`: `DATABASE_URL=postgresql://postgres:<POSTGRES_PASSWORD>@localhost:5434/auth`,
`REDIS_PORT=6381`, `REDIS_PASSWORD=<REDIS_PASSWORD>`, `PORT=3002`. Then
`npm run migrate && npm run start:dev`.

## Commands

The PR gates are `.github/workflows/ci.yml` (jobs `build-test`, `frontend`,
`docker`, `migrations`), `security.yml` (gitleaks), `codeql.yml`,
`dependency-review.yml`, `pr-title.yml`, and `devcontainer.yml` (builds the
Codespaces container when `.devcontainer/`, lockfiles or migrations change).

| What | Command | In CI |
|---|---|---|
| Install | `npm ci` | yes |
| Dev server (needs Postgres + Redis) | `npm run start:dev` | — |
| Lint (type-aware, size/complexity gates; **runs `--fix`**, so it may rewrite files) | `npm run lint` | yes |
| Build / typecheck backend | `npm run build` | yes |
| Unit tests (no DB needed, ~15 s) | `npm test` | yes |
| One test file | `npm test -- src/oauth/__tests__/refresh-keeps-audience.spec.ts` | — |
| Coverage (ratchet floor in `jest.config.js`) | `npm run test:cov` | — |
| Format backend code (`src/`) | `npm run format` | — |
| Format check (prettier, `src/`) | `npm run format:check` | yes |
| Secret scan | `gitleaks detect --source . --config .gitleaks.toml --redact -v` | yes |
| Apply migrations (needs DB) | `npm run migrate` | yes (`migrations` job) |
| Frontend install | `cd frontend && npm ci` | yes |
| Frontend god-file gate (300 code lines/file) | `cd frontend && npm run check:size` | yes |
| Frontend noindex parity gate | `cd frontend && npm run check:noindex` | yes |
| Frontend typecheck | `cd frontend && npm run typecheck` | yes |
| Frontend build | `cd frontend && npm run build` | yes |
| Frontend dev server (port 3003) | `cd frontend && npm run dev` | — |
| SDK packages | `cd packages/sdk && npm ci && npm run typecheck && npm run build` (same for `packages/resource`) | no |

Known gaps — do not rely on them: `npm run test:e2e` points at a
`test/jest-e2e.json` that does not exist (issue #244); `frontend`'s
`npm run lint` (`next lint`) no longer exists in Next 16 and is not a gate;
Prettier is enforced on backend `src/` only — `frontend/`, `packages/` and
`scripts/` are not formatted or checked. The Docker image and migration-path jobs need Docker and run
in CI only.

**Done = `npm run lint`, `npm run format:check`, `npm run build`, `npm test` green (and the four
frontend gates if you touched `frontend/`), PR title is a Conventional
Commit, CI green.**

## Architecture map

- `src/main.ts` — bootstrap: helmet/CSP, CORS, sessions (Redis), URI
  versioning, Swagger at `/docs` and `/openapi.json`. Port `PORT` (default 3002).
- `src/app.module.ts` — wires modules; JWT signing is RS256 when
  `JWT_PRIVATE_KEY` is set, HS256 (`JWT_SECRET`) only outside production.
- Request flow: Express middleware (`src/common/request-context.middleware.ts`)
  → guards (`src/auth/guards/`, throttlers) → controller (HTTP only) →
  service (logic) → `PrismaService` (`src/prisma/`) / `RedisService`
  (`src/common/redis.service.ts`) → `AllExceptionsFilter`.
- Routes are versioned in the decorator: `@Controller({ path: 'oauth',
  version: '1' })` → `/v1/oauth/*`; `VERSION_NEUTRAL` for `/.well-known`,
  `/scim/v2`, `/agents`, `/health`.
- `src/oauth/` — authorize/token/userinfo/revoke/introspect, PAR, DCR,
  device flow, DPoP, mTLS, token exchange, agents, API keys.
- `src/auth/` — login methods (passkey, magic link, OTP, password, wallet,
  federation, SAML) and the guards. `src/identity/` — DID, wallets, 2FA,
  account export/delete. `src/session/` — session listing/revocation.
- `src/admin/`, `src/rbac/`, `src/organizations/` — admin API and RBAC.
  `src/scim/` — SCIM 2.0. `src/ssf/` — CAEP / Shared Signals.
  `src/audit/` — audit log + webhook. `src/email/` — SMTP + templates.
- Operator-tunable flags (`*_ENABLED`, TTLs) are declared in
  `src/common/settings/settings.registry.ts` (env value, overridable from
  Admin → Settings). Boot-time env checks live in `src/common/env.validation.ts`.

Where to add things:

- **New endpoint** — a method on the module's controller (or a new
  `*.controller.ts` registered in its `*.module.ts`), logic in a service,
  DTOs with `class-validator` in the module's `dto/`. Controllers must not
  import `src/prisma` (lint enforces it).
- **New setting / feature flag** — an entry in `SETTINGS_REGISTRY` (types
  `flag` / `duration` / `csv` / `text`), read through the global
  `SettingsService`: `settings.flag('X_ENABLED')`,
  `settings.value('X', fallback)` (example: `src/scim/scim.guard.ts`). Add it
  to `.env.example`; secrets never go in the registry (env-only).
- **New migration** (red zone) — edit `prisma/schema.prisma`, add
  `prisma/migrations/NNNN_description/migration.sql` generated against a
  migrated DB (`npm run migrate` then
  `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`;
  needs a DB — use the Codespace). CI's `migrations` job proves fresh,
  tracked and untracked upgrades end at exactly `schema.prisma`. See
  `docs/MIGRATIONS.md`.
- **New UI page** — `frontend/app/<route>/page.tsx` (App Router), shared
  pieces in `frontend/components/`, API calls through `frontend/lib/api.ts`
  (relative `/v1`; in production Traefik routes `/v1` to the backend, so
  `npm run dev` alone serves pages but not API calls). Pages that must not be
  indexed need a noindex layout (`check:noindex`). Docs pages are
  `frontend/app/docs/<slug>/page.mdx`.

## From idea to PR

The loop an agent runs **with** the human (Claude Code: `/contribute` runs it):

1. **Restate** the idea in plain words; ask at most 3 clarifying questions.
2. **Locate** it: which files, which zone (table above). Search open issues
   (`gh issue list --search "<words>"`) — maybe it exists or is a
   `good first issue`.
3. **Spec** it briefly: problem, user-visible behaviour, API/UI change, data
   change, risks (security, Triad contract, migrations), out of scope.
   **Red zone → stop here**: open an issue with the spec using the "Product
   idea" template and wait for a maintainer's approval.
4. **Plan** small steps, each leaving the tree green.
5. **Implement with tests**, tests first where practical; put them in the
   module's `__tests__/`.
6. **Run the gates** (Commands → "Done =").
7. **Update docs**: README / `docs/` / `frontend/app/docs/` / `.env.example`
   for anything a user or operator sees. Not `CHANGELOG.md` — release-please
   writes it from commit messages.
8. **Commit** with Conventional Commits — release-please derives the version
   and changelog from them: `feat(scope): …`, `fix(scope): …`, `docs: …`,
   `test: …`, `refactor: …`, `chore: …`, `ci: …`; `!` after the type (or a
   `BREAKING CHANGE:` footer) for breaking. The body explains *why*.
9. **Open a PR** (`gh pr create`; without push access, `gh repo fork
   --remote` first and push to your fork) with `.github/PULL_REQUEST_TEMPLATE.md`
   filled — including a plain-language summary a non-engineer can follow.
   The PR title is the squash commit, so it must be a Conventional Commit
   (`pr-title.yml` checks it).

## Conventions

- **TypeScript, NestJS idioms**: one `@Injectable` per file, `kebab-case`
  file names (`device-flow.service.ts`), DTOs in `dto/`, small typed
  contracts in `contracts/`.
- **ESLint hard gates** (`eslint.config.mjs`): max 300 code lines per file,
  200 per function, max 3 params (pass an options object), complexity 12,
  cognitive complexity 30, no `any`, no floating promises. The only accepted
  disable is `max-params` on a NestJS DI constructor or decorated route
  handler, with the reason inline
  (`// eslint-disable-next-line max-params -- NestJS DI constructor …`).
- **Prettier** (`.prettierrc`): single quotes, trailing commas, width 100.
- **Comments** explain *why*, often citing the RFC (`RFC 8707: …`). Keep that
  density; don't narrate *what* the code does.
- **Errors**: Nest `HttpException`s; OAuth endpoints answer RFC error codes
  (`invalid_grant`, `invalid_client`, …) — keep them spec-exact.
- **Logging**: `private readonly logger = new Logger(X.name)`; never log
  token values, secrets or full request bodies.
- **Branches**: `type/short-topic` (`fix/refresh-reuse`, `docs/agent-ready`).
- **PR size**: one concern per PR; split refactors from behaviour changes.

## Testing

- Jest + ts-jest (`jest.config.js`): any `*.spec.ts`, by convention in
  `src/<module>/__tests__/` (some under `dto/__tests__/`). The whole suite runs in
  ~15 s with no database — Prisma, Redis, SMTP are hand-written stubs.
- Good examples: `src/oauth/__tests__/refresh-keeps-audience.spec.ts` (a
  security property: audience survives rotation, constructs the real service
  with stubbed Prisma/JWT) and `src/oauth/__tests__/dpop.service.spec.ts`.
- Fixtures: `fakeSettings({...})` from
  `src/common/settings/settings.test-fixture.ts` for anything reading
  settings.
- Mock only external systems; never mock the thing under test.
- Name the `describe` after the behaviour (`'refresh rotation keeps the RFC
  8707 audience'`), with a short comment on the bug or RFC rule it guards.
- CI also boots the Docker image against an empty Postgres and verifies every
  migration path; those need Docker and are checked on the PR.

## When to ask a human

- Anything in a red zone, before writing code.
- A change to what a token contains, who may get one, or how it is verified.
- A new dependency, a new env var that is required in production, or a
  change to defaults operators rely on.
- A test fails and the fix would change asserted security behaviour.
- The idea conflicts with SECURITY.md, the Triad contract, or an open issue.
- You'd need to touch CI workflows, the Dockerfile, or `deploy/`.
- You're unsure — asking is cheaper than a reverted auth change.
